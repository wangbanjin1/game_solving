QoE 双向带宽模拟与博弈求解代码仓深度导读

本文档专为接手和二次开发本项目设计。从业务背景、目录定位、每个源文件的输入输出与核心函数，到 MOS 计算公式、对偶价格博弈、资源协调算法细节，以及动手修改代码的精准定位指南。

1. 业务背景与系统定位

本项目面向无线蜂窝网络（基站小区，Cell）中的个人用户双向（Uplink / Downlink）带宽资源调度与体验质量（QoE / MOS）优化。

核心物理与业务约束：
  • 双向独立资源池：基站上行（UL）与下行（DL）各有固定物理容量上限（默认各 120,000 kbps = 120 Mbps），上下行带宽互相独立，不能互相挪用。
  • 个人粒度决策：每个用户对应一个活跃业务（一人一业务），按个人状态（套餐、业务、位置、容忍度、App、当前带宽、历史体验）进行多维度决策。
  • 套餐优先级（VIP 优先）：仅保留 普通用户（Normal） 与 VIP 用户 两类（第 6 期已移除 SVIP）。优化目标核心是无条件优先保障 VIP 用户的 App 级质差条件和目标 MOS；普通用户只消费保障 VIP 后的剩余资源。
  • 体验衡量指标（MOS 与 KQI）：MOS 范围为 1.0～5.0（严重卡顿到极致流畅）；质差保障规则使用 20～100 分制的 avgQoe（即 avgQoe = MOS × 20，阈值 50/60/70 分别对应 MOS 2.5/3.0/3.5）。
  • 零外部三方库依赖：全套算法和生成代码完全运行在 Python 3.10+ 标准库之上（仅使用 math, dataclasses, json, csv, random, hashlib 等），具备极致的可移植性与确定性重现能力。

2. 整体架构与分层设计

工程严格遵循领域驱动设计（Domain-Driven Design, DDD）分层理念与依赖注入（Dependency Injection），保证模型数学计算、约束策略判断、数据仿真生成、博弈求解算法、基准评估校验之间的高度解耦：

🏛️ 系统分层架构与数据流全景

1. Application 应用层

pipeline.py / cli.py / services.py
负责 CLI 命令分发、完整流程生命周期管理（生成 -> 求解 -> 评估 -> 写出）、依赖注入容器组装。

2. Domain 领域层

entities.py / validation.py / ports.py
不可变数据实体（Scene, User, Stream, Bandwidth, Action）、纯接口契约、输入 Schema 严格校验。

3. Models 体验模型层

mos.py / lookup.py
MOS 核心正算公式与反推所需带宽。支持参数化经验公式（Type A/B）与高精度的 CSV 关联表查表模型。

4. Optimization 优化博弈层

solver.py / policy.py / coordinator.py / candidates.py
对偶影子价格迭代、有限动作集构建与 Pareto 剪枝、超限修复、余量回填、字典序目标排名与收敛判断。

5. Simulation 仿真生成层

generator.py / population.py / sampler.py / assembler.py
基于种子和随机流的人口分布抽取、固定环境与 MOS 档位条件采样、带剪枝回溯的容量组场器。

6. Evaluation 评估校验层

validation.py / reference.py / metrics.py / comparison.py
全量方案独立数学复算校验、小规模暴力枚举全局参考（Brute-force Reference）、WGR 计算与前后对比报表。

4. 领域层 (game_solving/domain) 文件详解

game_solving/domain/entities.py 核心实体

文件定位：不可变领域模型（Immutable Domain Records）。全仓数据流转的标准契约。

关键数据结构：

  • Bandwidth(ul, dl): 带有 ul 和 dl 浮点数的带宽对象，支持 +, - 和 fits(capacity, tolerance) 容量容差判断。
  • Stream: 单个传输方向的不可变环境：码率 bitrate_kbps、分辨率 resolution、画面宽高 width/height、rtt_ms、丢包率 loss_ratio、卡顿率 stall_ratio、缓冲 buffer_ms。
  • User: 单个用户画像：user_id, business (业务类别), package ("vip" 或 "normal"), position (近/中/远), tolerance (高/中/低), app_id (54个具体App之一), current (当前上下行带宽), observed_mos (当前实测MOS), baseline (保障底线MOS), target (目标MOS), contract (最低签约带宽)。
  • Scene: 一个基站小区的完整场景切片：scene_id, capacity (总容量Bandwidth), users (用户元组), available 属性（自动扣除未建模占用 unmanaged 和预留 reserve）。
  • Action: 用户的一个候选动作：分配的上下行带宽、各方向预测 MOS、会话体验值 experience、净效用 h、预测的 KQI 字典 predicted_kqi、VIP 质差是否满足 quality_guarantee_met、质差违规项 quality_violations。
  • SolveResult: 求解器输出结果对象：包含最终方案 decisions、停止原因 stop_reason、迭代跟踪 trace、耗时与工作量。
⚠️ 避坑提醒： 所有领域实体均为 frozen=True dataclass。如需修改实体属性，必须使用 dataclasses.replace(instance, **kwargs)，切勿直接赋值！
game_solving/domain/validation.py 数据校验

文件定位：进入系统前的数据边界防线。在输入数据加载、生成后落盘前严格校验格式与物理量合法性。

核心函数：

  • validate_scene(scene, config): 校验小区可用容量是否大于 0、用户列表非空、用户 ID 唯一、业务类型是否存在于配置文件中、签约带宽与保障门槛合法性。
  • validate_stream(stream): 检查码率是否在合法区间、丢包率/卡顿率是否在 [0, 1] 闭区间、RTT 是否非负。
game_solving/domain/ports.py 接口端口

文件定位：定义微小抽象协议（Duck-typing / Protocols），规范体验模型（ExperienceModel）、候选动作生成器（CandidateProvider）、资源协调器（Coordinator）的调用契约。

5. 体验模型层 (game_solving/models) 文件详解

game_solving/models/mos.py 参数化 MOS 模型

文件定位：经典的理论公式模型（MosModel）。包含业务分类（Type A/B）、视频通话专用模型、单向 MOS 正算与根据目标 MOS 逆向反推所需带宽。

核心方法：

  • forward(business, stream, budget=None) -> float: 输入单向 Stream 参数，经过单项打分（$s_b, s_r, s_l, s_s$）、维度打分（$Q, I, V$）和动态加权（$\alpha, \beta$），计算输出 [1.0, 5.0] 区间的 MOS。
  • inverse(business, target, stream, budget=None) -> InverseResult: 给定目标 MOS $M^\star$，固定非码率环境，解析反推达到该目标所需的最小码率 $b_{\text{req}}$。若超出该分辨率的最大码率则报告不可达。
  • dimensions(business, stream) -> dict: 计算并返回 $Q$（画质评分）、$I$（交互评分）、$V$（流畅度评分）及动态加权系数。
game_solving/models/lookup.py CSV 离散查表模型

文件定位：第 6 期引入的基于离线测算数据的查表模型（LookupMosModel，标识为 lookup_table_v1）。彻底打通了实际业务中带宽与 MOS、时延、丢包、卡顿的离散对应关系。

核心实现机理：

  • _load_forward(): 从配置指定的 lookup_directory/forward/ 目录加载各业务的 CSV 映射表（包含带宽 Mbps、分辨率、典型时延 ms、典型丢包率%、典型卡顿率%、MOS 典型值）。
  • _load_choices(): 从 lookup_directory/reverse/ 目录加载反推目标 MOS 对应的推荐带宽。
  • lookup_row(business, stream): 在正向表中按业务、阶段和码率执行最近邻匹配。对手游（game），基于时延、丢包、卡顿加权欧氏距离匹配最优样本行。
  • project_stream(business, stream, rate): 当分配带宽改变为 rate 时，自动从查表行中投影出对应的预测时延、丢包率、卡顿率和分辨率，作为 predicted_kqi 的基础！

6. 优化与博弈求解 (game_solving/optimization) 文件详解

game_solving/optimization/solver.py 博弈求解器主循环

文件定位：算法核心中枢。实现对偶影子价格迭代（Dual Decomposition / Price Iteration）、分组 MOS 起跑线对齐、调用协调器并管理多轮收敛与熔断。

主循环核心时序：

  1. 初始化与硬条件预检查：校验场景，保存当前状态锚点。通过 certificate() 检查全员最低签约带宽与基本保障可行性，确定求解模式（NORMAL、DEGRADED 或 UTILITY）。
  2. 构建候选池：调用 CandidateBuilder.build() 为每个人生成有限 Pareto 候选池。
  3. 进入外层价格循环（迭代 $k = 0 \dots K_{\max}-1$）：
    • 确定候选作用域：CandidateBuilder.scope() 控制候选集逐轮由当前状态向外扩展。
    • 个人提案生成（第 1 轮）：每人根据当前资源价格 $\boldsymbol{\lambda} = (\lambda_{\text{UL}}, \lambda_{\text{DL}})$，最大化局部净收益：$\text{Score}_i(a) - \frac{\lambda_{\text{UL}} B_{\text{UL}} + \lambda_{\text{DL}} B_{\text{DL}}}{b_{\text{ref}}}$。
    • 分组 MOS 起跑线对齐（第 2 轮起，k+1 >= group_start_iteration）：同组用户（同套餐、容忍度、位置、业务、App、初始 MOS 档）选择同一公共目标 MOS 线，再映射回个人可执行动作！
    • 资源协调（Coordinator）：将全体用户的原始提案总需求与基站容量比对，超限时触发两阶段协调器（超限修复 $\to$ 余量回填 $\to$ 多施主效用交换）。
    • 对偶影子价格更新：根据协调前的超额需求与容量偏差更新上下行价格 $\boldsymbol{\lambda}^{(k+1)}$。
    • 记录与历史最优保存：字典序比较当前方案与历史最好方案，若更优则更新 best。
    • 收敛与终止判断：检查策略变化率、资源变化率、效用变化率；检查循环状态（STOPPED_CYCLE）；检查工作步数与超时。
  4. 最终状态终检与结果构造：消耗预留预算执行独立终检，封装返回 SolveResult。
game_solving/optimization/policy.py 优化策略与质差保障

文件定位：系统的价值判断中枢。定义用户权重计算、动作硬约束判断、VIP 质差保障规则、效用函数 $H_i$ 与方案字典序排名。

核心实现细节：

  • group_key(u): 返回用户的六元组分组键：(package, tolerance, position, business, app_id, initial_mos_band)。
  • quality_guarantee(u, b, direction_mos, predicted_kqi): 第 6 期核心质差保障判断器！ 仅针对 VIP 用户。依据 applications 配置中的规则，检查：
    1. avg_qoe $\ge$ avg_qoe_min（注意是 20～100 分制）
    2. service_delay_ms < service_delay_max_ms
    3. stalling_duration_seconds_proxy ≤ stalling_duration_max_seconds
    4. 上下行带宽是否达到 bandwidth_min_kbps 或分方向底线
    若不满足，返回 (False, violations_tuple)，记录具体违规原因（如 AVG_QOE, SERVICE_DELAY, BANDWIDTH_DL 等）。
  • weight(u): 多维混合基数权重（Mixed-radix order）。当 weight_mode == "ordered" 时，严格满足：套餐权重 > 业务大类 > 位置 > 容忍度。前一个维度的优先级完全压制后续维度的组合贡献！
  • rank(users, actions, mode): 比较两套分配方案优劣的字典序元组。在 vip_guarantee 目标下，优先级顺序为：
    (VIP 质差未满足人数, VIP 基本保障缺口总和, -VIP 总效用, -全员总效用)
game_solving/optimization/candidates.py 候选动作构建与剪枝

文件定位：为每个用户从连续的带宽空间中离散化出高质量候选动作集合，并通过 Pareto 支配剪除无效动作。

生成流程：

  • 基于配置的 mos_grid（如 1.0, 2.0, 2.5, 3.0, 3.5, 4.0, 4.5, 5.0）、用户的目标 MOS、保障底线 MOS 以及偏移量（$\pm 0.1$），调用模型 inverse() 反推得到对应的离散带宽点。
  • 合并当前带宽锚点、合同下限、媒体规格上下界、App 质差底线带宽。
  • 上下行笛卡尔积组合，生成原始候选。
  • 双资源 Pareto 剪枝：如果候选 $b$ 相比候选 $a$，在上下行资源均不大于 $a$、体验 $e$ 不小于 $a$、各方向 MOS 均不低于 $a$、稳定性惩罚不大于 $a$ 且至少有一项严格更优，则 $a$ 被严格支配并剔除！
  • 保留数量截断：按优先保留硬条件/保底动作、其次按效用降序，最多保留 kept_candidates_per_user 个（默认 128 个）。
game_solving/optimization/coordinator.py 与 utility_coordinator.py 资源协调器

文件定位：求解器中的关键执行器。当用户的个人自私提案导致基站带宽超载时，以最小的效用损失修复超载；并在存在带宽余量时执行升级与交换。

双协调器对比：

  • coordinator.py: 基础协调器，按 QoS 阶段（Non-GBR、GBR）与保护层级逐级回收带宽并进行升级。
  • utility_coordinator.py: 现代高效的净效用协调器（coordinate_utility）。包含：
    • 容量修复（Capacity Repair）：贪心搜索能有效减少当前超载方向带宽、且“单位释放带宽带来的效用损失最小”的动作进行降级替换，直到满足容量。
    • 余量升级（Slack Upgrade）：在容量允许下，寻找效用增益大于 $\epsilon$ 的单人升级动作。
    • 多施主效用交换（Bounded Net-Utility Exchange）：当单人升级空间耗尽时，枚举 1 个或 2 个施主（Donor，让出少量带宽）与 1 个受主（Receiver，获得带宽并带来大幅度效用跃升或消除 VIP 质差），执行联合替换！
game_solving/optimization/feasibility.py、prices.py、budget.py

辅助优化模块：

  • feasibility.py: 独立构造每个人满足硬条件、基本保障和目标条件的最小资源动作向量，用于预检查和证明是否存在全域不可行证据（Infeasible Certificates）。
  • prices.py: update_prices()，实现双方向影子价格的平滑阻尼更新（支持 legacy, smoothed, monotone 三种模式）。
  • budget.py: 统一的计算预算管理器 Budget，记录工作步数，支持预留 $4N+1$ 终检步数，防止死循环和超时。

7. 数据生成仿真 (game_solving/simulation) 文件详解

game_solving/simulation/generator.py 生成编排器

核心职责：负责大批量场景的数据合成（DatasetGenerator）。从人口生成、配额分配、状态池采样到场景组装，并衍生不同余量比例的场景家族。

余量场景派生机制（Headroom Ratios）：当 capacity_mode == "current_headroom" 时，生成器先抽取每个用户的初始状态，计算当前全员总带宽 $B_{\text{used}}$，然后根据配置的 headroom_ratios: [0.0, 0.01, 0.03, 0.05]（0%、1%、3%、5%），将基站容量设为 $B_{\text{used}} \times (1 + \text{ratio})$，派生出用户完全一致但拥塞程度递进的场景家族！

game_solving/simulation/population.py 人口采样器

核心算法：

  • counts(n, probs): 最大余数法（Largest Remainder Method / Hamilton Method）。将浮点概率转换为严格等于总人数 $n$ 的整数，杜绝四舍五入导致的“缺人”或“超人”。
  • allocate_with_minimums(n, probs, minimums, rng): 保底覆盖分配器！例如专项配置为“开直播”强制保底 10 人，为 54 个 App 各自保底至少 1 人，确保罕见业务与边缘 App 均有样本。
game_solving/simulation/sampler.py 与 assembler.py

核心实现：

  • sampler.py (ConditionalSampler): 固定网络环境抽取（时延、丢包、卡顿三档质量分布）、指定 MOS 档位（超额/达标/不达标/严重不达标）下的码率反推与复核。
  • assembler.py (assemble): 带下界剪枝的有限回溯组场器。使用剩余用户最小带宽的后缀和 $\sum B_i^{\min}$ 作为强下界剪枝，高效搜索出同时满足基站上下行物理容量的合法初始用户状态组合。

8. 评估与基准比对 (game_solving/evaluation) 文件详解

game_solving/evaluation/validation.py 独立终检复核器

核心价值：算法安全底线。完全不信任求解器内部声称的结果，从最底层的 Scene 和每个分配动作重新执行数学公式复算！

复核内容：用户数量是否吻合、动作上下行带宽总和是否严格低于可用容量（容差 0.001 kbps）、每个用户的码率是否与 MOS 公式重新正算结果绝对一致、签约带宽是否被突破。一旦发现违规立即抛出异常阻断流程。

game_solving/evaluation/reference.py 离散暴力枚举参考求解器

核心功能：针对小规模场景（如 4 人验证），不使用启发式价格迭代，直接对所有人的离散候选动作全空间展开全局暴力搜索（Brute-force），找到全局真正的离散最优解，用于计算启发式算法的加权收益改善比（Weighted Gain Ratio, WGR）。

game_solving/evaluation/comparison.py 与 metrics.py

核心功能：提取求解前后对比数据（初始 vs 返回），计算 VIP 达标人数净增、VIP 质差满足率变化、MOS 改善/恶化人数分布，并渲染为清晰的 Markdown 对比报告（comparison.md）。

10. MOS 正向与反推数学公式设计

系统内置两套体验计算逻辑：参数化经验公式（Type A / Type B）与离散查表模型（Lookup Table）。

10.1 通用单项评分（Single-Metric Scores）

设媒体码率为 $b$ (kbps)，分辨率标量为 $r$，往返时延 RTT 为 $\ell$ (ms)，丢包率为 $p \in [0,1]$，卡顿率为 $s \in [0,1]$：

sb = 5.0 / (1.0 + exp(-b / 928.984))       # 码率质量评分
sr = 5.0 / (1.0 + exp(-r / 410.0))         # 分辨率质量评分
sl = 1.0 + 4.0 * exp(-180.94 * p)          # 丢包流畅度评分
ss = 5.0 - 4.0 * s                         # 卡顿流畅度评分

10.2 综合维度评分与 A/B 类非线性聚合

将单项分按业务权重 $w_1, w_2, g_1, g_2$ 综合为三大维度：

  • 画质评分 $Q$: $\text{clip}(5 - 4w_1(5-s_b) - 4w_2(5-s_r))$
  • 交互评分 $I$: $1 + 4\exp(-0.0035\ell)$ （初始阶段为首缓公式）
  • 观看流畅度 $V$: $\text{clip}(5 - 4g_1(5-s_l) - 4g_2(5-s_s))$

根据交互与流畅度自适应计算动态非线性敏感度权重 $\alpha_{\text{mos}}, \beta_{\text{mos}}$：

alpha = 0.1 * (1.0 + 2.0 * exp(-I / 2.0))
beta  = 0.1 * (1.0 + 2.0 * exp(-V / 2.0))

# A 类业务（点播、短视频、开直播、看直播、会议）：乘积归一化
MOS_A = 1.0 + (Q - 1.0) * (alpha * (I - 1.0) + beta * (V - 1.0)) / (4.0 * (alpha + beta))

# B 类业务（云游戏、视频通话、手游）：扣分惩罚机制
MOS_B = clip(1.0 + (Q - 1.0) * (1.0 - alpha * (5.0 - I) - beta * (5.0 - V)))

10.3 目标 MOS 反推带宽（Inverse）

当给定用户期望达到的目标 $M^\star$ 时，固定该用户的环境 $I, V$ 及对应参数，反解出画质所需门限 $Q^\star$：

$$Q^\star = 1 + \frac{4(M^\star - 1)(\alpha + \beta)}{\alpha(I - 1) + \beta(V - 1)}$$

进而反推所需码率分 $s_b^\star$，并通过 Logit 函数的解析逆变换求得精准连续码率，最后向上按 bandwidth_quantum_kbps 进行量化并正算复核。

11. VIP 质差保障与 54-App 规则（第 6 期增量核心）

VIP 质差保障四大铁律（由 policy.py 的 quality_guarantee 执行）：

只有满足以下全部 4 项条件的 VIP 用户动作，才被判定为“质差保障满足”：

  1. avgQoe >= avg_qoe_min：使用 20～100 分制（系统内 MOS $\times 20$）。普通游戏/视频要求 60 分（MOS 3.0），快手/淘宝等要求 70 分（MOS 3.5），视频通话/会议要求 50 分（MOS 2.5）。
  2. serviceDelay < service_delay_max_ms：如王者荣耀要求 < 60ms，原神要求 < 100ms，三角洲行动要求 < 80ms。
  3. stallingDuration <= stalling_duration_max_seconds：视频与直播类要求卡顿总时长代理 ≤ 2.0 秒。
  4. bandwidth >= bandwidth_min_kbps：指定方向或分方向带宽门槛（如咪咕快游下行 ≥ 1800 kbps，开直播抖音上行 ≥ 1500 kbps，B站开直播上行 ≥ 4000 kbps）。

六维用户分组（Group Key）

在求解器第 2 轮起，全体用户按照以下 6 个维度归并为一个 Group，并在 Group 内部协商同一公共 MOS 起跑线：

group_key = (
    user.package,      # 1. 套餐: vip / normal
    user.tolerance,    # 2. 容忍度: high / medium / low
    user.position,     # 3. 距离基站距离: near / middle / far
    user.business,     # 4. 业务大类: shortvideo, game, meeting 等
    user.app_id,       # 5. 具体 App: 如 wangzherongyao_game, douyin_svod
    initial_mos_band   # 6. 初始 MOS 所在分段区间: int((observed_mos - 1.0) / width)
)

12. 对偶影子价格与博弈迭代

算法采用对偶分解（Dual Decomposition）思想，将基站小区层面的集中式耦合带宽约束，转化为各用户分布式自主决策的影子资源成本：

12.1 用户个体净效用函数 $H_i$ 与选择打分

用户 $i$ 采用归一化体验 $e_i = (M_i - 1)/4 \in [0, 1]$。其自身净效用 $H_i$ 定义为：

$$H_i = (w_i + \eta \cdot \text{debt}_i) e_i - \beta |\Delta e_i|$$

  • $w_i$：基于套餐、业务、位置、容忍度的混合基数归一化权重。
  • $\eta \cdot \text{debt}_i$：历史欠账公平补偿因子（历史体验落后目标越多，当前权重补偿越高）。
  • $\beta |\Delta e_i|$：稳定性惩罚（防止频繁抖动变动）。

在当前轮次给定的影子价格 $\boldsymbol{\lambda} = (\lambda_{\text{UL}}, \lambda_{\text{DL}})$ 下，用户的决策评分为：

$$\text{DecisionScore}_i(a) = \text{Score}_i(a) - \frac{\lambda_{\text{UL}} B_{i,\text{UL}}(a) + \lambda_{\text{DL}} B_{i,\text{DL}}(a)}{b_{\text{ref}}}$$

其中 VIP 用户若满足质差保障，会获得额外的 vip_guarantee_bonus 奖励加分，促使其主动倾向于选择合规动作。

12.2 影子价格更新法则（Subgradient Price Update）

汇总所有用户未协调前的原始请求总带宽 $B_{\text{raw}, d}^{(k)} = \sum_i B_{i,d}^{\text{raw}}$。按步长 $\gamma_k = \frac{\gamma_0}{\sqrt{k+1}}$ 迭代：

$$\lambda_d^{(k+1)} = \max\left(0, \; \lambda_d^{(k)} + \frac{\gamma_0}{\sqrt{k+1}} \cdot \frac{B_{\text{raw}, d}^{(k)} - C_{\text{avail}, d}}{b_{\text{ref}}}\right)$$

超载方向的价格上升，促使下一轮用户自发减少该方向的带宽需求；空闲方向价格下降趋于 0。

13. 协调器：修复、余量回填与效用交换

用户独立的自私最优提案求和可能突破基站容量，必须由协调器（utility_coordinator.py）进行无缝修复：

第 1 步：超限贪心修复

只要总带宽超过可用容量，计算各用户换选动作带来的有效带宽释放量 $R_i$，优先选择“单位释放带宽所损失效用最小”的动作替换，直到上下行全部满足物理容量限制！

第 2 步：空闲余量升级

基站容量出现富余时，遍历所有候选动作，在不超限的前提下，优先将带宽升级给效用增益最大的用户（VIP 质差改善具有绝对优先权）。

第 3 步：多施主效用交换

当单人升级无缝隙时，启发式寻找 1~2 个带宽充裕的用户作为“施主”（Donor，让出 100~200 kbps），转赠给 1 个“受主”（Receiver，获得带宽后达成 VIP 质差合规或产生巨大效用）。只要净效用收益 $> \epsilon$，即执行联合原子替换！

14. 收敛判据、循环检测与三类预算熔断机制

14.1 收敛判定（CONVERGED_LOCAL）

连续 stable_rounds（默认 3 轮）同时满足以下条件：

  • 策略变化比例 $\varepsilon_{\text{strategy}} = \frac{1}{N} \sum_i \mathbf{1}[a_i^{(k+1)} \ne a_i^{(k)}] \le 0.01$
  • 资源分配变化 $\varepsilon_{\text{resource}} \le 0.0001$
  • 总净效用变化 $\varepsilon_{\text{utility}} \le 0.0001$
  • 价格变化 $\le \varepsilon_{\text{price}}$ 且局部动作与交换检验通过。

14.2 策略循环检测（STOPPED_CYCLE）

维护每轮策略向量、价格与价格信号的三元组签名集合 seen。如果检测到曾经出现过的状态再次出现（如 A -> B -> A），认定算法陷入非线性循环震荡，立即安全终止，并提取历史最优可行解返回！
