2. 初期超调的两大成因剖析

初期超调不是算法 Bug，而是“局部候选集逐轮外扩”与“对偶价格指数平滑惯性”在离散博弈下必然产生的动态物理响应：

机制一：动作空间逐轮外扩 (Scope Expansion)

在第 1 轮，求解器为了实现安全平稳启动，强制将搜索邻域限制在用户当前状态周边极窄的带宽/MOS 窗口内（由 initial_mos_band_width 限制）。此时高带宽动作处于锁定状态。

第 2 到第 5 轮，外围的高速率动作按轮次递增逐步解禁。更高带宽能带来更高 MOS 以及达标奖励。因此，随着动作解禁，全体用户在本地微观利益驱动下争相申请高带宽顶级档位。

机制二：对偶价格反应的平滑滞后 (Smoothing Lag)

系统最终出清容量所需的真实影子价格约为 λDL ≈ 0.078。而第 1 轮给定的初始试探价仅为 λDL(1) = 0.005。

为了防止价格像过山车一样震荡，系统配置了 price_smoothing = 0.25 以及步长上限 price_max_step = 0.02。在前 5 轮，高带宽档位已被解锁，但带宽“买路费”依然极低（λ < 0.025），造成了短期的超调冲顶。

关键结论： 图中的“超调”纯属用户端意向需求（Raw Requested Bandwidth）；而基站实际下发分配带宽（Allocated Bandwidth，图黄色虚线）从第 2 轮开始一直死死卡在容量红线 977.8 Mbps，物理容量从未发生过超配！

3. 价格平滑机制详解（代码与数学）

3.1 文档原始次梯度与工程平滑的演进

在规范文档 docs/个人用户双向带宽_数据模拟与博弈求解方案.md 第 9.7 节中，原始设计的对偶价格更新为标准次梯度更新：

λdk+1 = max(0, λdk + γk · (Bdraw,k - Cd) / Bref,d)

次梯度在离散档位下的致命缺陷（Bang-Bang 效应）： 因为用户只能在有限离散码率（如 500k, 1000k, 1500k）中选择，一旦超载，次梯度单步加价过猛，会导致下一轮所有普通用户瞬间全部弃购，总需求跌至谷底；价格随即归零，下下一轮又全体冲顶。

3.2 工程落盘实现：一阶惯性平滑滤波（EMA）

代码落盘于 game_solving/optimization/prices.py，其具体执行逻辑为： 

def update_prices(prices, demand, capacity, iteration, previous_signal, config):
    cfg = config["solver"]
    for j, direction in enumerate(("ul", "dl")):
        excess = getattr(demand, direction) - getattr(capacity, direction)
        residual = excess / max(getattr(capacity, direction), 1.0)
        # 死区控制：微小超额（如 <= 1%）不调价，避免微观抖动
        residual = 0.0 if abs(residual) <= cfg["price_deadband"] else residual

        # 核心：一阶指数加权移动平均 (EMA) 平滑滤波
        alpha = cfg["price_smoothing"]  # 默认 0.25
        value = alpha * residual + (1 - alpha) * previous_signal[j]

        # 步长计算与削峰限幅 (Clipping)
        step = cfg["gamma0"] / math.sqrt(iteration + 1) * value
        step = min(cfg["price_max_step"], max(-cfg["price_max_step"], step))  # 限制在 [-0.02, 0.02]

        updated.append(max(0.0, prices[j] + step))

平滑系数 α (0.25)

新拥塞信号只占 25%，历史价格趋势惯性占 75%，彻底抹平离散选档带来的价格锯齿。

死区阈值 (0.01)

需求在容量 ±1% 内不调整对偶单价，使收敛状态能够稳定停驻。

单步上限 (0.02)

单轮最大价格变动不超过 0.02，避免任何突发极端信号破坏已有解的局部性。

4. 效用函数 Hi(a) 的完整构成

每个用户在给定候选动作 a 时，所获得的净体验收益 Hi(a) 定义在 game_solving/optimization/policy.py（第 285 行）：

Hi(a) = (wi + ηfair · hi) · ei(a) - βchange · |ei(a) - eianchor| - ciswitch(a)
项名称 数学定义 / 取值 物理业务意义与设计考量
归一化体验 ei(a) (min(MOSUL, MOSDL) - 1.0) / 4.0 将 [1, 5] 分的 MOS 线性映射到 [0, 1] 的无量纲收益。双向业务以较差的一侧为准。
静态权重 wi VIP: 6 / 普通: 4（除以基准 6） VIP 的基础调度优先级高于普通用户，保障其基础资源倾斜。
长期公平欠账 hi clip((MOStarget - MOShistory) / 4, 0, 1) 衡量用户在过去滑动窗口（300秒）内遭受的历史委屈程度。
公平增益因子 ηfair 配置值：0.5 将历史欠账转化为当前即时边际效用的放大倍数。
稳定性惩罚 βchange 配置值：0.1 惩罚动作偏离当前网络初始基准状态的幅度，抑制频繁跳档。
切换信令开销 ciswitch 默认值：0.0 跨承载或切片变更的信令开销。

5. 深度答疑：长期公平惩罚为什么不能直接写成 +η · (MOStarget - MOShistory)？

核心疑问剖析： 直觉上，“过去用户亏了多少，就在当前效用里直接加上 + η · (MOS_target - MOS_history) 予以补偿”，这是最朴素自然的想法。但在运筹优化和分布式博弈中，如果直接作为一个独立常数项相加，该项在数学上会彻底失效！

致命失效原因 1：对用户选择动作毫无区分度

假设我们直接把原式写成独立相加的形式：

Hi(a) = wi · ei(a) + η · (MOStarget - MOShistory) - 稳定性

请注意：对于用户 i 而言，其历史观测 MOShistory 和目标 MOStarget 是进入当前调度轮次前就已经发生过的既定事实（纯固定常数），与用户当前轮选动作 a1（低带宽）还是 a2（高带宽）完全没有任何关系！

当用户在比较动作优劣做差分时：

Hi(a2) - Hi(a1) = wi · [ei(a2) - ei(a1)] + 0

常数项直接相减抵消！用户无论选 1 Mbps 还是 5 Mbps，这个加项的分数一模一样，用户根本没有任何动力因为历史欠账去申请更高的带宽。

致命失效原因 2：基站协调无法产生调度倾斜

基站在小区容量紧张进行资源协调时，依据的是单位带宽带来的体验增益率（边际收益率）：

ImproveRate = ΔH / ΔB = (wi · Δe) / ΔB

常数项由于对 ΔB 的导数为 0，根本不会进入边际改善率的计算分子中。

结果是：基站协调器在计算时，完全感觉不到这个用户曾经受过委屈，依然会把宝贵的空闲带宽优先分给信道条件更好、提分更容易的其他用户，长期饥饿问题依然得不到任何解决。

5.2 系统的优雅解法：把欠账变成权重的“放大乘数”

为了让历史欠账真正变成调度推力，系统将欠账归一化为 hi = clip((MOStarget - MOShistory) / 4, 0, 1)，然后乘到了当前动作的即时体验 ei(a) 上：

Hi(a) = [wi + ηfair · hi] · ei(a) - 稳定性惩罚

业务效果对比：从“发死工资”转变为“边际提权”

  • 没有历史欠账的用户 (hi = 0)：其体验提升斜率仅为基础权重 wi（例如 1.0）；
  • 历史严重受损的用户 (hi = 0.5)：其体验提升斜率变成了 1.0 + 0.5 × 0.5 = 1.25（提权 25%）！
  • 调度的物理实现：由于斜率被放大，该用户每多拿 1 Mbps 带宽，为系统贡献的 ΔH 远大于其他用户。基站在对偶价格出清与资源回填时，就会自动把带宽优先调度给历史欠账用户！

5.3 全局目标闭环推导证明（规范文档第 6.4 节）

在宏观全局层面，系统定义全网未补偿的历史损失为： Cfair = ∑i hi · [1 - ei(ai)]（即欠账越严重且当前体验越差，系统受到的惩罚越大）。

系统最大化的全网总优化目标为：

J = ∑i wi ei(ai) - ηfair Cfair - 稳定性惩罚

将 Cfair 代入并展开：

J = ∑i [wi + ηfair hi] ei(ai) - 稳定性惩罚 - ηfair ∑i hi
J = ∑i Hi(ai) - 常数项

由于最后一项 ηfair ∑ hi 是进入本次求解前由历史决定的常数，因此最大化全网目标 J 严格等价于最大化个体效用总和 ∑ Hi！ 这证明了乘积形式不仅物理含义完美，在数学上更具有严格的变分一致性。

6. 体验稳定性惩罚的物理意义

稳定性惩罚项为：β_change · |e_i(a) - e_i^anchor|（配置值 β_change = 0.1）。

为什么要惩罚与初始锚点的偏差？

  1. 消除 Ping-Pong 频闪效应：用户对画质的剧烈起伏极其敏感（例如从 1080P 跌到 360P 又跳回 720P）。
  2. 抑制微小的无益跳档：如果一个动作只能带来 MOS +0.05 的微弱提升（Δe = 0.0125），但打破了现状，稳定性惩罚会扣除 10% 的收益。只有当升档带来的改善显著大于扰动代价时，系统才允许调档。
  3. 天然的阻尼保护：在多轮迭代的价格平衡边界，稳定性惩罚为“维持原状”提供了天然阻尼，彻底杜绝了全网几百个用户在相邻档位间集体来回震荡的现象。

7. 微观决策与宏观出清全景

求解器每轮让每个用户在本地最大化其综合决策分（扣除对偶价格成本）：

maxa [ DecisionScorei(a) - (λUL BUL + λDL BDL) / 1000 ]
  • VIP 用户：DecisionScore = 100.0 · 1{质差达标} + Hi(a)
  • 普通用户：DecisionScore = 0.001 · Hi(a)

为什么第 11 轮会发生“断崖式回落”并精准收敛？

  1. 第 1~5 轮（价格过低）：λDL = 0.005。即使要 5000 kbps 带宽，扣费也仅有 0.025 分。普通用户的 0.001 · H 能够覆盖这个成本，VIP 用户更有 100.0 的达标分撑腰，大家蜂拥要顶档，推高 Raw 需求至 1350M。
  2. 第 6~10 轮（价格稳健攀升）：超额残差通过平滑滤波持续累加，对偶价格从 0.025 涨到 0.078。
  3. 第 11 轮（出清临界点）：当价格越过 0.075 门槛时，5000 kbps 的扣费高达 0.375，远超普通用户的残差效用；普通用户瞬间被“价格挤出”，主动退缩回 200~300 kbps 的业务保底档；而 VIP 用户凭借 100.0 的质差奖励硬顶对偶价格，死死守住达标带宽。
  4. 结果：需求在 1 轮内瞬间收缩至 958 Mbps，完美满足基站物理容量，求解器宣布局部收敛！
