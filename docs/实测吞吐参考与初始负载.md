# 实测吞吐参考与初始负载

用户提供的观测：5 台手机使用 iperf 打流，合计上行约 120 Mbps、下行约 120 Mbps。尚未确认两个方向是否同时测试；没有逐台实测分布。这是压测量级参考，不是 QoE 需求标定、单用户最大速率或小区容量证明。

120 Mbps = 120000 kbps。除以 5 得到 24000 kbps，只作为构造高负载样本时的参考尺度。不能据此把每个用户的业务占用设为 24 Mbps，也不能按模拟人数乘以 24 Mbps 设置小区容量。

## 代码中的使用方式

`generation.throughput_reference` 保存观测来源、设备数和双向合计速率。`generation.high_load_sampling` 控制高负载提案：默认关闭；`congestion_qoe.json` 对有配置的媒体业务启用 20% 的提案概率。

下面是模拟假设，均可调整，并非实测得出的业务需求：

| 业务 | 高负载提案起点 / 参考平均速率 | 当前起点 |
| --- | ---: | ---: |
| 短视频、会议、开直播 | 0.125 | 媒体方向 3000 kbps |
| 长视频、观看直播、云游戏 | 0.25 | 媒体方向 6000 kbps |

提案只选择现有媒体模型能够覆盖该起点的分辨率，范围上限继续由原业务媒体配置决定；不放大 MOS 公式，不扩大未经支持的码率范围。生成器仍按目标达标档位反推码率并正向校验 MOS。高负载起点仅影响初始采样，不是优化过程的最低保障，求解仍可降到原媒体模型允许的下限。

语音和普通游戏不套用此高负载起点。短视频等仅在媒体方向采样高负载，反方向保留业务自身规则；会议分别生成双向状态。因此初始上下行通常不相等。

20% 是每次合适业务提案的概率，不保证最终恰好 20%：业务分布、MOS 档位与模型可行性都会影响接受率。`scenes.jsonl` 的用户审计记录保存 `high_load_sample`，`generation_report.json` 保存参考参数与接受的高负载样本数；该数量包含各余量场景中重复的同组用户。

## 人数与容量

人数由 `population.users_per_cell` 决定。先按仅 QoE 业务分布、套餐和体验档位生成这些用户，再分别求和得到初始占用 B_ul、B_dl。人数改变影响样本总需求，不能保证实际无线吞吐随人数线性增长。

同组场景共用用户状态与历史，按 r ∈ {0, 0.05, 0.10, 0.15, 0.20} 设置：

`小区总上限[d] = B[d] × (1 + r) + 非受控占用[d] + 预留[d]`

这是为比较算法而构造的容量条件，不是对实测无线系统容量的预测。120 Mbps 不参与容量上限公式，也不要求初始总占用凑到 120 Mbps。旧的 4 人精确参考配置继续使用原采样条件，用于暴搜正确性对照。
