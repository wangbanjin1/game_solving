# 拥塞场景、总效用目标与参考答案

## 2026-09-20 App 分组与资源不足专项设计

专项配置 `configs/congestion_qoe_9_20_1.json` 使用 300 人、普通/VIP 两档套餐和 0%/1%/3%/5% 初始资源余量。人口生成先按 QoE 大类整数化，再在业务内分配 App；当该业务人数不少于 App 数时，每个 App 至少分配 1 人。当前目录含 54 个 App 规则，覆盖游戏、云游戏、开直播、视频通话、长视频、会议、看直播和短视频。常规 `congestion_qoe.json` 仍作为百人回归基线。

分组键固定为 `(套餐, 容忍度, 距离, 业务大类, App, 初始MOS分档)`，初始 MOS 默认每 0.5 分一档。第 1 轮按个人初态搜索，避免把不同起点直接混为一个角色；第 2 轮起，每个组先选一个聚合收益最好的共同 MOS 线，再把该线映射到成员各自的合法候选。容量协调仍允许拆分个体，因而分组降维不会绕过合同、媒体上下界和小区上下行容量终检。

`vip_guarantee` 目标先减少 VIP 的 App 级质差保障违例，再比较 VIP 效用和总效用。App 规则中的 `avgQoe` 按 `MOS×20` 映射；`serviceDelay` 使用固定环境的 RTT；由于当前输入只有卡顿比例而没有卡顿时长，`stallingDuration` 明确采用 `stall_ratio×10秒观察窗` 的代理值，不能解释为实测卡顿时长。带宽门槛按规则指定的 UL 或 DL 检查。非 VIP 不参与质差判定，仅以很小的剩余资源权重参与选择。

每个动作保存 `predicted_kqi`，逐轮用户记录保存请求/分配 KQI 及 `kqi_change_from_initial`。专项配置开启可审计的 KQI 响应层：码率跨过媒体档位最低门槛时切换到可承载的最高分辨率；若动作码率与初始码率之比为 $\rho$，则时延、丢包率和卡顿率分别按 $\rho^{-0.35}$、$\rho^{-0.6}$、$\rho^{-0.8}$ 调整，并受配置中的改善下限和恶化上限约束。MOS 使用响应后的分辨率、时延、丢包和卡顿重新正向计算。该响应层是仿真假设、尚未用现网数据标定，参数集中在 `kqi_response`，报告必须标注为预测 KQI，不能冒充实测值。

HTML 的“本轮分组决策”直接列出套餐、容忍度、位置、业务、App、初始 MOS 档、组内人数和共同 MOS 线；第一轮明确显示为个人初态对齐，第二轮起展示六维分组表。KQI 区域位于逐用户策略之前，同时给出初始值、本轮预测值与变化值。

当前实验入口仅为两个 `congestion_*.json` 配置；`default.json` 提供完整参数源。旧实验配置、数据集和报告已移出项目；必要的最小测试条件放在 `tests/fixtures`。

## 一致的评价目标

`policy.objective=total_utility` 表示在硬约束内最大化总 H；基本保障和期望目标作为统计及效用建模信息，不再通过降级模式的词典序规则覆盖 H。合同、禁止软降级等显式硬约束仍检查。旧配置默认 `legacy_guarantee` 保留历史结果语义。

当前 H 为：权重乘归一化体验 + 历史欠账补偿 - 相对初始状态的稳定性成本。没有引入未经定义的实际计费成本。影子价格参与个人请求，不从最终比较的 H 再扣一次，也不跨轮比较带不同影子价格的个人分数。

返回历史最好合法分配。`terminal_decisions` 保存最后完成轮次的分配，`returned_matches_terminal` 表示返回方案是否与它一致。`run_status=SUCCESS` 表示求解过程达到当前局部稳定判据，不证明不同于终态的返回方案也收敛，更不证明全局最优。终检重算返回方案的 MOS 和硬约束。

## 数据与容量

`generation.capacity_mode=current_headroom` 先选取各用户合法当前状态，再按当前上下行总和分别乘以 `(1+r)` 得到可用容量，最后加上预留和未管理占用形成样本总容量。`headroom_ratios` 默认 `[0,0.05,0.10,0.15,0.20]`。`num_scenes` 在此模式表示基础用户样本数，最终场景数乘以余量档数。

同一基础样本的五档容量共用用户、目标、权重、KQI 和历史。历史在最小余量容量下生成，保证它在所有容量版本中都合法；历史序列用于初始化补偿，仍不是在线多周期闭环。

`population.business_probs_by_package` 和 `generation.compliance_probs_by_package` 可按套餐配置业务和初始档位，未配置套餐回退全局分布。严格配额失败会报错，宽松模式在审计中记录 `quota_status=gap`，不能把期望比例当作实际比例。

`require_target_reachable=true` 要求每个接受的用户状态存在固定模型域内的达标动作；不保证它们同时满足小区总容量。`initial_distribution.jsonl` 另外记录全部目标是否联合可行，以及联合可行时的目标见证分配。这份见证不是效用最优答案。

## 已确认分布与实验假设

`congestion_qoe.json` 仅保留 QoE 业务计数，总数 594,370；排除 sa、sta，保留 `qoe_category`。由于开直播原始计数只有 20，纯比例整数化会得到 0 人；当前通过 `minimum_qoe_counts` 先保留 2 名开直播用户，其余 98 人再按原始比例分配。每个基础样本因此得到短视频 36、长视频 27、会议/云游戏/语音/观看直播/游戏各 7、开直播 2。该最低覆盖是实验覆盖约束，不代表开直播现网占比为 2%。

以下仅为本轮实验假设，配置 `extensions.experiment_assumptions` 明确标注：

- 套餐仅保留普通/VIP，专项样本为 210/90。
- 权重按套餐、业务、位置、容忍度排序；套餐为 VIP/普通，位置为远/中/近，容忍度为低/中/高。这些是偏好实验，不是确认的现网规律。

`policy.weight_mode=ordered` 用混合进位序号构造 w：高维度一个档位的变化超过所有低维度组合对单个用户权重的影响，再除以 `weight_reference`。套餐位于最高维度，单个 VIP 的基础权重高于任意普通用户。只有 VIP 进入目标达标和 App 质差保障统计；普通用户只保留体验与资源指标。

## 候选和协调

当前可执行控制域仍为固定 G、固定媒体及环境，只调有模型依据的媒体码率。没有新增可改变 RTT/丢包/卡顿的响应模型，因此不声称已实现原始方案中所有 KQI 自由组合。`candidate_mos_offsets` 在当前、基本保障、目标附近增加采样点，每个点经反推、正向校验后进入候选。参考枚举独立构造未经主算法 Pareto/数量截断的有限候选，并覆盖新增关键点。

新协调器先按有效释放资源的单位效用损失修复超额需求，再执行正效用增量的合法升级。供体按降级损失、接收者按升级收益筛选，检查一或两个供体支持一个接收者的净收益；每次交换后重新检查余量升级。`exchange_shortlist` 和 `exchange_pairs_per_iteration` 限制邻域，不能称为全空间局部最优证明；截断情况写入每轮记录。

## 价格和停止

`price_update=smoothed` 按各方向容量归一化协调前超额需求，使用指数平滑、死区、衰减步长和单步涨跌幅上限。需求超额时上涨，明显不足时允许下降。`monotone` 仅作为可选实验模式，不用于默认新实验，也不具有额外最优保证。

价格变化、用户动作、资源占用、H 和保障向量持续稳定、候选已展开，并在已评估邻域没有改进时停止。动作重复本身不再触发平滑模式循环判定，循环键还包含价格和滤波状态。最多 500 轮，但时间和总工作量任一上限仍可先停止。固定定额当前锚点和硬下界按动作 ID 去重，避免锚点标记差异使完整展开判定永久失败。

## 参考答案和日志

- `reference_results.jsonl`：`H_reference`、`policy_decisions`、候选数、完整性、工作量、耗时和 H 差距。`exact_discrete` 才表示声明的有限空间搜索完成。
- `U_reference/action_ids` 保留旧的加权 MOS 对照；H 的见证使用独立的 `policy_action_ids/policy_decisions`，两者不能混用。
- 新模式参考搜索以算法已验证方案作初始下界；大场景若超时且未找到更好解，参考 H 可能等于算法 H。这时不能声称误差为零或算法最优。
- `initial_distribution.jsonl`：各套餐及套餐×业务人数、VIP 初始达标/未达标、MOS/历史 MOS/KQI 分位数、VIP 个人目标不可达人数和联合目标见证。普通用户相关达标字段为不评价。
- `iteration_trace.jsonl`：逐轮请求、分配、效用分项、价格成本、相对初始 H 变化、资源交换事件和预算。
- `solve_results.jsonl` 内嵌紧凑轮次汇总，详细记录由 `detail_trace_file` 引用，避免重复存储逐用户日志。
- HTML 同时展示当轮 H、历史最好 H、参考 H、参考证明状态、终态/返回方案和初始套餐统计。

## 运行命令

小样本完整搜索：

```powershell
python -m game_solving generate --config configs/congestion_exact.json --output outputs/my_exact_data
python -m game_solving solve --config configs/congestion_exact.json --input outputs/my_exact_data/solver_inputs.jsonl --output outputs/my_exact_solve
python -m game_solving.visualization --input outputs/my_exact_solve --output outputs/my_exact_report.html
```

百人混合样本：

```powershell
python -m game_solving generate --config configs/congestion_qoe.json --output outputs/my_qoe_data
python -m game_solving solve --config configs/congestion_qoe.json --input outputs/my_qoe_data/solver_inputs.jsonl --output outputs/my_qoe_solve
python -m game_solving.visualization --input outputs/my_qoe_solve --output outputs/my_qoe_report.html
```

每次使用新的输出目录。单元及集成验证：`python -m unittest discover -s tests -v`。
