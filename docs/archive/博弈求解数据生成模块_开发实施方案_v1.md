# 博弈求解数据生成模块：开发实施方案 v1

> 本文依据用户给出的数据模拟流程、评测指标和附件《粘贴的 markdown (1)。md(20260909-135440)》编写，与前文《体验Agent博弈求解_开发实施方案_v1》衔接。
>
> 用户原始范围、模型假设、开发默认参数分别标识。原附件存在合并单元格丢失、列错位和缺项，以下按指标语义人工规范化，不建议运行时直接解析原表位置。
>
> 交付范围是可供开发的数据生成方案，不是已经生成的数据集。v1先提供可复现的小区快照、可选时间序列、求解器输入及独立评测标签。公式使用纯文本，不依赖LaTeX渲染。

## 1. 目标、边界与最终产物

模块需要生成一个完整的小区资源竞争场景，而不是互不关联的用户记录。每个场景应说明：有多少用户、使用哪些业务、权益和画像是什么、当前体验如何、当前资源是否可行、目标保障是否可行，以及算法可以改变哪些配置。

主流程保留为：

```text
配置小区规模
→ 生成用户与业务
→ 确定用户MOS目标区间分布
→ 条件采样KQI
→ 计算真实采用的MOS
→ 由带宽模型反解资源并正向复核
→ 校验全小区资源和分布
→ 生成数据、可选采样视图及评测标签
```

“真实采用的MOS”在本文指合成环境内部依据公式计算的值，不是现网实测值。所有合成结果使用 `source=synthetic`。

### 1.1 输出目录契约

```text
run_<id>/
  manifest.json                种子、配置、输入来源、版本与哈希
  resolved_config.json         展开默认值后的完整配置
  source_catalog.json          附件规范化范围及异常说明
  scenes.jsonl                 全量小区状态，一行一个快照
  solver_inputs.jsonl          求解器可见视图
  labels.jsonl                 评测私有标签、候选与参考解标识
  candidate_sets.jsonl         独立参考候选集，可按需输出
  generation_report.json       实际分布、拒绝原因、覆盖与缺口
  validation_report.json       单位、边界、容量、模型一致性结果
```

数据模块不负责现网下发。配置、样本、标签必须能通过 `scene_id` 和 `role_id` 精确连接。

## 2. 第一版开发约定

| 项目 | v1约定 |
| --- | --- |
| 网络范围 | 手机移动网单小区场景，不生成Wi-Fi或固网 |
| 用户与业务 | 默认一人一业务；一人多业务作为显式配置扩展 |
| 资源维度 | 每个场景一个明确方向的等效速率预算，单位Mbps |
| 用户隐性因素 | 合成环境可有设定真值，不能称作真实主观真值 |
| MOS模型 | 复用用户KQI公式与可替换总聚合接口 |
| 带宽模型 | 复用前文analytic_bandwidth_v1正反接口 |
| 随机生成 | 有种子、分阶段独立随机流、固定重试预算 |
| 全量与采样 | 先生成全量真值，再生成求解器可见采样视图 |
| 参考最优解 | 相同约束下有限候选集的联合最优，不是各用户分别最优 |
| 非重点业务 | 浏览/下载使用QoS或服务效用，不伪造视频MOS |

开播常涉及上行，观看常涉及下行。本版混合业务使用明确标记的 `abstract_direction` 测试预算，或按实际方向拆场景；不能把上下行实际容量相加后当成同一个可交换资源池。现网口径测试使用方向明确的数据。

## 4. 配置设计

### 4.1 小区规模

配置 `num_scenes`、`users_per_cell`、`capacity_mode`、`capacity_mbps`、未建模占用和预留比例。

开发演示档位，可自行替换：

| 档位 | 每小区用户数 | 用途 |
| --- | ---: | --- |
| tiny | 3～6 | 联合穷举参考 |
| small | 20～50 | 功能联调 |
| medium | 100～300 | 分布与采样 |
| large | 1000 | 性能测试，不默认精确求解 |

这些不是现网典型容量/人数结论。实际容量与人数共同决定难度，不能仅按用户数命名“高负载”。

### 4.2 用户—业务联合分布

优先接受完整联合概率表：

```text
P(套餐, 业务, 容忍度, 位置)
```

也支持条件表：

```text
P(套餐)
× P(业务 | 套餐)
× P(容忍度 | 套餐, 业务)
× P(位置 | 业务, 套餐)
```

用户只提供边缘比例时，v1明确采用独立近似；VIP容忍度固定不容忍，再对普通用户按高/中/低分配，避免抽到VIP高容忍。

同时传入不一致的联合表与边缘比例时：严格模式报错，不同时声称满足两者。需要拟合联合分布时应作为单独模式，不在v1静默补齐。

### 4.3 从比例生成整数人数

使用最大余数法：先取 `floor(N*p_i)`，剩余人数按小数余数从大到小补1，并以类别ID处理并列。

条件分布在每个父类人数下分别分配。能保证每层人数总和正确，但小样本无法保证每种组合都出现；覆盖要求超过人数时配置失败。

一人多业务模式下：套餐、容忍度、位置在用户层生成一次；业务层生成多个角色。所有统计明确区分用户数和业务实例数。

## 5. MOS分布规划

### 5.1 两套标签分开

**绝对体验档（附件文字，边界为实现约定）：**

| 档位 | 区间 |
| --- | --- |
| 很差 | [1,2) |
| 差 | [2,3) |
| 一般 | [3,3.5) |
| 良好 | [3.5,4.5) |
| 优秀 | [4.5,5] |

**保障达标档（相对用户目标）：**

令 `T=MOS_target`，离线默认 `delta_over=0.3`、`delta_severe=0.7`：

```text
严重不达标：MOS < T-delta_severe
不达标：    T-delta_severe <= MOS < T
达标：      T <= MOS < T+delta_over
超额达标：  MOS >= T+delta_over
```

每档与[1,5]求交；空档不可分配正人数。例如T=4.8时超额档为空，不能生成MOS5.1。

套餐目标演示默认：普通2.5、VIP4.0、超级VIP4.5，继承先前方案的项目设定。具体业务意图可以覆盖目标，必须记录来源。

### 5.2 指定配额

允许按“套餐×业务”设置四档比例，例如VIP会议：超额0.1、达标0.5、不达标0.3、严重0.1。以上是演示配置，不是推断现网比例。

先分配每档整数人数，后为对应用户搜索满足区间的KQI。最终存储：

- `requested_mos_band`：规划档；
- `mos_computed`：最终计算值；
- `realized_mos_band`：最终值所属档；
- `quota_status`：满足或未能满足。

不能为了凑达标率修改计算后的MOS。

### 5.3 浏览、下载

`mos_target=null, mos_computed=null`。以最低吞吐或浏览加载目标划分达标状态，单独统计QoS达标率。四档MOS配额只作用于有MOS模型的重点业务。

## 6. 根据MOS条件采样KQI

### 6.1 不采用不存在的唯一反函数

```text
MOS = f(KQI)
```

通常多组KQI对应同一MOS。因此“根据MOS采样KQI”实现为条件采样：提出KQI组合、运行模型、判断是否满足区间。

基础方法是分层提议＋拒绝采样；改善接受率可使用已校验候选池。不要训练一个未经验证的逆函数再将输出视为真值。

### 6.2 提议分布

1. 选择合法媒体档位或采样业务码率。
2. 选择质量状态提议（好/一般/差），作为影响KQI的共同隐变量。
3. 在各指标相应范围内采样；允许混合状态如高画质但高时延。
4. 运行MOS模型，满足目标档才保留为proposal。

默认混合质量提议率20%，其余共享大类分档。这是防止所有指标完全独立或完全同档的开发启发式，不代表真实联合分布。

媒体档位必须限制分辨率与码率组合，沿用 `media_profiles`。对于video缺码率，可临时定义360p/0.5Mbps、480p/0.8、540p/1.2、720p/2、1080p/4、2160p/12，全部标为 `demo_media_profile`；其他业务码率不得越过附件给定总体范围。

### 6.3 连续值与离散值采样

- 连续区间默认均匀采样，仅为可复现基线，不宣称拟合现网。
- 分辨率从给定集合采样，不生成不存在的633p。
- 区间使用 `min/max/include_min/include_max`，先在配置中保留开闭边界。
- 浮点值序列化前后都重新分档，避免把0.15001%舍入为0.15%而改变标签。
- 主数据浮点保留足够精度；展示格式另设字段。

边界测试另生成精确端点和相邻合法值，例如loss=0.0015属于好，略大于0.0015属于一般。它们属于边界套件，不要求被普通随机分布自然抽到。

### 6.4 零值

码率为0在附件范围内，可生成 `unserved`异常样本；不把其单项2.5分视为可用业务。零时延/零丢包可以作为公式边界测试，但在模型闭合主数据中是否可达，由模型底噪决定。

### 6.5 重试与失败

每角色默认最多2000次proposal，每小区最多10次整体生成尝试。耗尽返回 `MOS_BAND_UNREACHABLE_OR_LOW_ACCEPTANCE`，保留尝试数及最接近MOS。

严格配额模式：整场失败，写入报告，不输出假达标场景。

宽松模式：允许输出最接近的合法样本，但必须写真实档位和配额缺口；不能让报告仍显示100%配额满足。默认strict。

## 7. MOS模型与字段适配

直接导入前一开发方案的 `MosModel`，避免数据生成器与求解器各抄一份公式发生漂移。

单项公式版本固定为用户附件；五个参数组P1～P5、业务映射和总聚合分别版本化。临时聚合仍为Q/I/V等权平均，标记 `aggregation_source=demo`；这不是用户已确认的总MOS函数。

### 7.1 时延适配

保存：

```text
latency_value_ms
latency_semantics: interaction | end_to_end | rtt
rtt_proxy_ms
proxy_mapping: identity_demo | calibrated_mapping | measured_rtt
```

无确认转换关系时，离线可选 `identity_demo`，原数值当作评分输入，但必须标记只是代理。不能在文档或标签中声称端到端时延就是RTT，也不擅自乘2。

### 7.2 初始阶段

video可生成initial与steady；initial用缓冲评分，steady使用配置的RTT代理。meeting建立时延未给范围，默认steady；需要initial时显式补充 `meeting_initial_buffer_range` 并标为自定义。

game抖动保留在KQI中，当前MOS不使用它，输出 `unused_mos_metrics=[jitter_ms]`。

### 7.3 缺失值

基础ground_truth不随机缺失必需评分项。先生成完整状态，再对solver_inputs做缺失/噪声注入，复用原评分表已有回退规则并记录 `imputed`。

## 8. 由KQI反解带宽并保证闭合

### 8.1 沿用解析模型

复用前文接口：

```text
inverse(K_target, G, environment) → B_required
forward(B, media, G, environment) → K_predicted
MOS_final = f(K_predicted)
```

模型结构概要：

```text
R = bitrate_kbps/1000 + audio_mbps
C = B×efficiency/(1+overhead_ratio)
x = C-R

RTT = RTT_floor + a/x
loss = loss_floor + loss_amp×exp(-x/loss_scale)
stall = stall_floor + stall_amp×exp(-x/stall_scale)
buffer = buffer_floor + 1000×burst_mbit/C
```

B是等效服务预算，不是5QI本身。GBR/Non-GBR/5QI从合法profile目录生成，不能从KQI唯一反推一个5QI编号。

### 8.2 为什么还要正向复核

inverse按各KQI上限需要的最大余量求B，所以forward可能让其中一些指标优于原proposal。最终MOS也可能高于规划档。

主数据以forward输出为状态：

1. 保存proposal供审计；
2. inverse得到B；
3. forward得到K_final；
4. 重算MOS_final；
5. 确认K_final在业务允许总体范围内、MOS_final仍属于目标配额档；
6. 不满足就拒绝重采。

不要求K_final等于K_proposal，但要求满足proposal中的目标约束。绝不能保留proposal的MOS配额标签，又把另一组forward值作为当前状态。

### 8.3 原带宽默认模型与附件范围的冲突

前文默认 `loss_floor=0.0001, loss_amp=0.01`，其可产生丢包上限约0.0101，小于附件最大0.05；`stall_amp=0.10`也无法生成附件“差”档30%以上卡顿。默认RTT底噪30ms无法生成0～30ms。

因此不能宣称默认模型覆盖全部附件区间。v1提供两类套件：

| 套件 | 用途 | 闭合要求 |
| --- | --- | --- |
| `closed_loop` | 求解器资源优化主评测 | 必须通过inverse/forward和容量校验 |
| `range_boundary` | 公式、字段和边界测试 | 可覆盖全部源范围；没有闭合证据时不算WGR |

闭合套件的环境参数在生成场景前从配置中选择，不得逐样本为凑标签任意调整底噪。

示例额外仿真环境可设loss_amp=0.06、stall_amp=1.2、较小margin_min以覆盖更差状态；使用比例时将forward输出限制为0～1，并对目标范围做复核。该扩展版本记为 `analytic_bandwidth_sim_v1`，不是悄悄改变旧模型。参数仍可能使某些组合不可达，需要可达性预检。

### 8.4 可达性预检

在正式生成前，每个业务、公式组、阶段、环境组合先扫描有限媒体/余量网格，记录可达MOS区间和各目标档候选数。

某配置要求正人数的档没有候选时提前失败，并报告是分辨率上限、总MOS聚合、模型底噪还是带宽上限导致。有限扫描未发现不等于数学证明不可达，错误文案使用“当前搜索配置未找到可达候选”。

可达性池只用于提议和提高效率；使用缓存仍带独立随机微扰并重新闭合检查，报告重复率，避免大量完全重复样本。

## 9. 小区容量与负载生成

### 9.1 区分三个资源量

```text
B_current_sum = Σ当前已分配预算
B_target_sum  = Σ各业务达到目标的最低已知预算
B_available   = B_total-B_unmanaged-B_safety
```

正常快照必须满足 `B_current_sum<=B_available`。允许 `B_target_sum>B_available`，这表示保障需求冲突。

`B_target_sum`按有限候选估计时写 `best_known_target_requirement`；未找到某个业务目标配置则另标不可达，不能当作0加入。

### 9.2 模式A：先生成业务，再推导容量

默认用于遵循用户原生成顺序并严格控制当前MOS档配额：

```text
先完成各业务KQI/MOS/B闭合
抽取当前预算占用比例rho_alloc，0<rho_alloc<=1
B_available = B_current_sum/rho_alloc
B_total = B_available+B_unmanaged+B_safety
```

配置小区规模阶段确定容量策略和范围，最终在资源计算后落定数值。若超出配置容量范围，重采整场；禁止硬截断B_total导致超限。

此模式可以精确控制当前分布，但容量是派生的，报告不得写成容量与MOS分布彼此独立抽样。

### 9.3 模式B：容量固定

用户明确给定容量时，在该预算下尝试生成整个小区：

- 按业务最低合法需求预检人数与容量是否基本匹配；
- 逐用户生成时保留尚未生成用户的最低预算估计；
- 完成后检查当前总预算；
- 超限时重采或执行明确的 `regenerate_under_budget`模式，并重新计算全部KQI/MOS与配额；
- 限次失败报告配置冲突，不统一缩小B后保留旧MOS。

严格固定容量、固定人数、固定MOS比例可能不可同时满足，这是需要显式返回的生成结果。

### 9.4 负载标签

使用两个独立标签：

```text
allocation_ratio = B_current_sum/B_available
baseline_pressure = B_target_sum/B_available
```

演示阈值：allocation_ratio≤0.6为低，(0.6,0.85]为中，(0.85,1]为高；baseline_pressure>1标记目标压力超限。这些是测试标签，不是标准拥塞判定。

等效配置预算占用不等于实测PRB利用率或实际流量利用率，字段名不能写成真实无线利用率。

## 10. profile、位置与容忍度

### 10.1 profile状态

按 `P(profile | business, package)`生成当前profile，但只从配置允许集合抽取。离线使用demo profile，真实5QI未配置时为null并设置 `executable=false`。

当前profile作为锚点，候选profile由前述求解器合法邻接表控制。默认不同profile没有人为固定体验提升；如模拟差异，必须作为环境版本参数记录。

### 10.2 合成隐性因素

对每个用户生成：

```text
tolerance_true, position_true
```

这里的true只代表合成器设定。需要模拟画像误差时再生成 `tolerance_observed/position_observed`，依据配置混淆矩阵抽样。

基础套件二者相同；噪声套件显式指定误差，不擅自把“较近”转换为较低RTT。位置影响权重，是否进一步影响环境效率必须另设开关，以免重复加入效果。

### 10.3 权重口径

复用前一方案的权重函数和版本，不能生成器与求解器各自计算不同权重。

评测默认固定使用场景开始时的 `w_eval`；算法改变动作不能改变评测权重。画像有噪声时分别记录 `w_input`与`w_eval`，前者供求解器、后者用于合成真值评测。

## 11. 时间序列与长期指标

单快照用于资源可行性和短期收益，不足以评价历史补偿或稳定性。

可选 `sequence_mode`：生成同一用户集合多个真实周期，套餐和身份固定，业务活动/位置/负载按配置转移；每周期沿用同一组模型参数或明确环境变化事件。

- 默认演示周期5秒、60周期，可配置。
- 静态用户不能每周期重新随机抽套餐。
- MOS_history由前序已实现轨迹按时长计算，不能独立随意填值。
- 无历史时使用前方案的中性初始化。
- 各算法回放同一外生轨迹，但各自配置和MOS历史独立演进。
- 初始流阶段只能在业务开始时出现，不因求解器内部迭代更新。

时间序列默认每周期用前一状态加有界扰动/转移生成提议，再经本周期模型闭合与容量校验。不能给同一个固定业务任意抽取完全独立的KQI跳变并声称连续观测。

## 12. 全量真值和采样视图

先在scenes生成全量角色，每角色 `n=1,p=1`。然后构造求解器视图：VIP全保留，普通用户按业务、套餐、容忍度分层抽样；是否加入位置分层可配。

对非空层g：

```text
总体N_g，抽样n_g
p_g=n_g/N_g
每个被抽角色代表人数=1/p_g
```

聚桶时 `population_weight=sample_count/p`，不再把总体数当sample_count。

- 目标与资源均使用同样放大倍数。
- 参考解与评测总体使用全量真值。
- 必须把样本/群体决策映射回全量后再评测，不能只评价被抽样者。
- 默认同桶统一策略并逐个复核个体可行性；不一致则拆桶、按个体修复，并报告修复损失和失败率。
- 标签与全量隐藏信息不放入solver_inputs。
- 未抽到的非空层不得权重为0隐去，需补采或显式合并。

## 16. 最优参考解与WGR

### 16.1 保留用户WGR定义

对同一评测用户集合，使用固定w_eval：

```text
U_cur = Σ w_u×MOS_cur_u
U_alg = Σ w_u×MOS_alg_u
U_opt = max Σ w_u×MOS_u(a_u)

WGR = (U_alg-U_cur)/(U_opt-U_cur)
```

这里不归一化MOS，与用户给定指标保持一致；权重版本固定。缺少MOS的浏览、下载不加入这三项，但它们占用的资源与约束必须参加联合求解。

### 16.2 U_opt必须是联合优化

有限参考候选集下：

```text
每个角色选择一个候选a_u
最大化 Σ重点角色 w_u×MOS_u(a_u)
约束：Σ所有角色 B_u(a_u)<=B_available
      套餐/基本保障/用户聚合/合法profile/可执行动作范围均满足
```

不能“每人遍历选最好的KQI，然后相加”，因为各人的最好状态可能争用同一份带宽。

参考候选集由独立网格生成，不能只用待测算法剪枝后的候选，否则剪错的答案永远发现不了。tiny场景可枚举笛卡尔积；较大场景使用离散优化或分支定界，必须记录停止状态、界和gap。

### 16.3 参考最优的范围

- `exact_discrete`：在给定有限候选集、模型和约束下证明最优。
- `best_known`：只找到较好可行解，不能字段名冒充U_opt。
- `upper_bound`：上界不能当可实现MOS总分。
- `not_computed`：仅评估约束和改善。

只有有效且可比的exact_discrete才默认输出 `WGR_exact`。best_known可输出 `relative_gain_to_reference`，不得称最优增益实现率。

### 16.4 连续动作与参考集可比性

严格WGR套件要求算法从共享的有限动作宇宙选动作，独立oracle可以在完整宇宙搜索，算法可自行剪枝。若算法输出连续新动作，应加入参考宇宙重新求解，或不报告“精确WGR”。

### 16.5 当前方案可行性

若当前方案不满足参考优化的硬底线，U_cur不是可行下界，U_opt可能低于U_cur。此时仍报告绝对加权MOS变化与SLA改善，但WGR标记 `invalid_baseline`。

开发默认将当前真实状态作为候选保留；只有其满足参考约束时，才能保证离散最优不低于当前值。

### 16.6 分母和异常

```text
D = U_opt-U_cur
D <= epsilon：WGR=null，reason=no_valid_improvement_denominator
算法结果不可行：WGR=null，记录约束违例
可比条件通过：按原式计算，不截断到[0,1]
```

WGR<0表示退化。严格可比环境下WGR>1说明候选、模型或参考求解有不一致，应触发检查，不把结果裁成1。

### 16.7 目标函数与求解器不完全相同

前述求解器还考虑历史补偿和稳定性。纯加权MOS的U_opt只衡量“纯体验改善空间”，不一定是求解器真实目标的最优。

另输出同一稳定性参照、历史和权重下的 `H_alg/H_ref`，与前文不含价格的H一致。lambda是内部资源协调价格，不进入最终真实收益比较。

## 17. 用户增长数与补充指标

“用户增长数”按用户正文解释为MOS提升人数，不等于网络新增用户数。

```text
N_improved = count(MOS_alg-MOS_cur > epsilon_mos)
N_worsened = count(MOS_cur-MOS_alg > epsilon_mos)
N_unchanged = 其余具有可比较MOS的用户数
```

默认 `epsilon_mos=0.01`，开发阈值可配。

更贴近保障目标的指标：

```text
新增达标人数 = count(MOS_cur<T 且 MOS_alg>=T)
失去达标人数 = count(MOS_cur>=T 且 MOS_alg<T)
净达标增量 = 新增达标人数-失去达标人数
```

一人多业务时同时输出业务实例计数；用户计数默认“所有活跃重点业务均达标”，不得重复数同一用户。

另外记录：总资源违例、各套餐达标率、非重点QoS达标率、可回收量、配置变更数、求解时间、采样修复损失。不能只报改善人数而隐去被降级用户。

## 18. 防止模型自证与标签泄漏

同一解析模型生成和评价，只能说明算法在该合成模型下有效。默认报告 `evaluation_environment=matched_model`。

可增加 `mismatched_model` 套件：求解器使用公开估计参数，评测环境使用预先抽取且隐藏的真实参数；算法动作统一在隐藏环境重算，再比较。隐藏参数不能被传入solver_inputs或借历史未来值泄漏。

不要为某算法动作临时调整环境；同场景各算法面对同一外生条件。匹配模型与失配模型成绩分别报告。

训练/验证/测试按scene或sequence分组，不随机拆用户行。来自同一个基础场景的容量变体、噪声变体也归同一split，避免模板泄漏。标签、参考最优动作、最终目标资源、隐性真值默认不在输入中。

## 19. 可复现与性能

配置根种子后，用稳定散列从 `(seed, scene_index, attempt, stage, role_id)`派生随机流，阶段包含population、quota、kqi、environment、noise、sampling。

不能使用随进程随机化的语言内置hash。并行任务完成顺序不改变输出内容，最终按scene_id排序写出。

manifest保存配置哈希、源码版本、依赖锁文件哈希、源目录版本、模型版本。重启可按scene_id续跑，输出原子写入临时文件后重命名，避免半行JSON。

生成复杂度主要由 `场景数×角色数×KQI尝试数×模型计算`决定。参考最优解成本单独计时，默认只对tiny套件计算精确解。

## 21. 最小闭合数值样例

沿用前文带宽参数和稳态媒体：码率2000kbps、分辨率720p、音频0.128Mbps；提议RTT80ms、丢包0.001、卡顿0.01。

反解得到B约3.581503Mbps，正向KQI约为：RTT51.714724ms、丢包0.000730957、卡顿0.01。对于P4与临时Q/I/V等权聚合，使用这些正向值重算最终MOS，不能继续使用提议RTT80ms算出的旧MOS。

实际复算得到Q约4.332413、I约4.337736、V约4.860891，最终MOS约4.510347；若目标4.0、超额阈值0.3，则属于超额达标。该结论仅适用于此处的P4、临时聚合与参数版本。若整个小区三个相同角色，则当前资源合计约10.744509Mbps；选择allocation_ratio=0.8时，派生可用容量约13.430636Mbps。

## 23. 开发顺序与完成定义

1. **配置与范围目录：**完成源表规范化、单位转换、整数配额和字段schema。
2. **模型与条件采样：**复用MOS/带宽适配器，实现预检、拒绝采样及正向复核。
3. **小区场景：**实现固定/派生容量、严格失败路径、全量数据输出。
4. **采样与标注：**生成输入视图、独立候选和tiny联合参考解，实现WGR异常处理。
5. **扩展测试：**时间序列、画像误差、模型失配和性能档位。

第一版完成的标准不是“生成了足够多JSON”，而是每条成功场景都可追溯、资源自洽、MOS可复算、配额真实、失败可解释，且能直接转换为前一方案的CellSnapshot和RoleState。
