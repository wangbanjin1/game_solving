01 · 先建立项目全貌

项目解决的问题是：在一个共享上下行资源池中，为每名用户从有限合法动作中选择一组带宽，使总用户效用最大，同时保证容量和个人硬约束成立。

max H = max Σ Hᵢ(aᵢ)

构造候选
协调资源
评价报告
输入用户、业务、套餐、KQI、当前带宽、小区容量
决策每名用户的上下行带宽动作
输出MOS、效用、达标状态、资源占用、收敛证据
当前100人实验：5个基础样本，每个样本派生0%、5%、10%、15%、20%五档余量，共25个场景。

05 · 核心数据对象

从 domain/entities.py 开始。先理解对象，再进入算法。

类表示什么关键字段
Bandwidth一组上下行资源ul、dl
Stream一个媒体方向码率、分辨率、RTT、丢包、卡顿、上下限
User一个用户的完整求解状态业务、套餐、位置、容忍度、当前带宽、目标、历史
Scene一个小区场景用户、容量、预留、非受控流量、模型哈希
Action一个候选或最终动作带宽、方向MOS、总MOS、效用、达标状态
InverseResultMOS反推结果是否可达、带宽、复算MOS、失败原因
SolveResult一个场景的求解结果决策、停止原因、轨迹、证据、工作量
对象关系：Scene包含User，User包含一个或多个Stream；求解器为每个User选择一个Action。

07 · MOS模型和候选动作

MosModel.dimensions()计算画质Q、交互I、观看V和聚合因子。
MosModel.forward()从码率和KQI正向计算MOS。
MosModel.inverse()反推达到目标MOS的最小量化码率。
b*(M) = min { b : MOS(b) ≥ M }

候选动作构造

optimization/candidates.py 中的 CandidateBuilder负责：

  1. 保留当前锚点、基本保障和目标动作；
  2. 加入最低、最高、当前码率；
  3. 加入统一MOS网格、用户目标和上下邻近点；
  4. 分别反推上下行码率并组合；
  5. 调用Policy.make_action()删除非法组合；
  6. 执行双资源Pareto剪枝；
  7. 最终限制每名用户最多128个候选。

scope()在迭代过程中逐步开放更远的MOS层级，使早期搜索更稳定。

08 · 权重、效用和求解算法

Policy：规则中心

optimization/policy.py 中的 Policy负责权重、硬约束、动作构造和全局方案排序。

方法职责
weight()套餐 → 业务 → 位置 → 容忍度混合进位权重
hard_errors()合同、媒体范围、用户上限、固定定额、硬MOS检查
make_action()从Bandwidth生成完整Action并计算效用
rank()比较两组全局分配方案
Hᵢ = (wᵢ + 0.5Dᵢ)Eᵢ − Cᵢ

Solver：主循环

optimization/solver.py 中的 Solver.solve()是算法主入口：

可行性预检
生成候选池
个人请求
资源协调
更新价格
判断收敛
aᵢ⁽ᵏ⁾ = arg max [ Hᵢ(a) − (λUL·bUL + λDL·bDL)/1000 ]

当前100人实验的实际协调路径

当前目标是total_utility，因此求解器进入 UTILITY 模式，实际协调实现位于 utility_coordinator.py：

  1. 按单位有效资源的最小效用损失修复超载；
  2. 接受容量允许的正效用升级；
  3. 尝试一个或两个供体支持一个接收者；
  4. 只接受净效用严格提高且容量合法的交换。

prices.py负责影子价格更新；budget.py统一限制工作量和时间。

11 · 想改什么，应该去哪里

修改目标首选位置通常是否需要重新生成
用户数、套餐和业务比例configs/*.json → population是
开直播保底人数population.minimum_qoe_counts是
会议分辨率和码率businesses.meeting.media是
RTT、丢包、卡顿范围ranges是
套餐目标MOSpolicy.targets / baselines是
套餐优先公式Policy.weight()模型指纹变化，需重新生成
MOS公式models/mos.py是
候选MOS粒度solver.mos_grid / candidate_mos_offsets可直接对同一输入重新求解，但建议单独版本记录
候选剪枝CandidateBuilder.build()重新求解
超载修复与交换utility_coordinator.py重新求解
影子价格prices.py和solver配置重新求解
评价指标evaluation/metrics.py通常需重新求解或重算结果
HTML页面visualization/*.html只需重新生成报告

13 · 推荐的第一次修改练习

先做一次只改配置的候选粒度实验，观察配置如何影响候选数量、工作量和最终效果。

步骤

  1. 复制configs/congestion_qoe.json为configs/learning_qoe.json。
  2. 把candidate_mos_offsets从[0.1]改为[0.05, 0.1]。
  3. 使用新输出目录重新生成和求解。
  4. 比较summary.json、comparison.md和iteration_trace.jsonl。
python -m game_solving generate --config configs/learning_qoe.json --output outputs/learning_qoe_data
python -m game_solving solve --config configs/learning_qoe.json --input outputs/learning_qoe_data/solver_inputs.jsonl --output outputs/learning_qoe_solve

重点观察

候选数量细化MOS目标后，每个用户候选池是否明显增大。
工作量与时间max_steps和max_solver_ms怎样变化。
最终收益weighted_mos_gain和达标人数是否真正改善。
学习闭环：每次只改一类参数，保留旧输出，再比较输入、求解轨迹和结果。这样最容易定位一项修改到底影响了哪一层。
